# CHG-083 完了タスク遅延読み込み

## 変更ID

CHG-083

## 変更内容

Cotaska の起動時タスク読み込み対象を、原則として「未完了タスク」と「直近の完了タスク」に限定し、古い完了タスクは必要になったタイミングで追加読み込みする。

## 変更理由

現在は起動時に全タスクファイルを読み込み、完了済みの古いタスクもメモリキャッシュと renderer 表示モデルの対象になる。タスク件数が増えるほど起動時 I/O、メモリ使用量、renderer 変換、検索対象生成の負荷が増えるため、通常作業に必要な範囲を先に読み込み、履歴データは遅延読み込みにしたい。

## 想定仕様

### 初期読み込み対象

- `status != done` のタスクは全件読み込む。
- `status == done` のタスクは、直近分のみ読み込む。
- 直近分の判定には、現行 `_index.yaml` にある `updated_at` を利用する。
- `_index.yaml` のサマリー情報だけで読み込み候補を選別し、古い完了タスク本文を起動時に読まずに済むようにする。
- CHG-083 では、遅延読み込みのためだけに `_index.yaml` の項目を増やさない。
- 将来、完了日そのものを厳密に扱う機能が必要になった場合は、別仕様変更として `_index.yaml` の項目追加を検討する。

### 古い完了タスクの扱い

- 完了ビューでは、初期表示分を超える古い完了タスクは自動読み込みしない。
- 表示しきれない完了タスクは「次を読み込む」などのボタン操作で追加読み込みする。
- 検索では、古い完了タスクも初期状態から検索対象に含める。
- ただしアプリ起動時に古い完了タスク本文を全件読み込むのではなく、検索実行時に必要な範囲を読み込む、または検索用の軽量情報を使う方式を検討する。

### キャッシュ方針

- `taskService` は「読み込み済みタスク」と「インデックス上は存在するが未読み込みのタスク」を区別できるようにする。
- 未読み込みタスクの詳細表示、復元、再オープンなどの操作前には対象ファイルをオンデマンドで読み込む。
- watcher 経由で未読み込み完了タスクが変更された場合は、必要に応じてサマリー更新または読み込み済み化する。

## 影響範囲

- UI: 完了ビュー、検索ビュー、タスク詳細表示、件数表示
- API/IPC: タスク取得 API に読み込み範囲または追加読み込み API が必要になる可能性がある
- main process: `taskService`, `indexService`, `watcher`
- renderer: `App.jsx`, `taskViewModel`, 完了ビュー・検索ビューの表示制御
- データ: タスクファイル正本と `_index.yaml` のスキーマは変更しない。現行 `_index.yaml` の `status` と `updated_at` を初期読み込み対象の選別に利用する

## 完了条件

- 起動時に古い完了タスク全件を読み込まない。
- `_index.yaml` のスキーマを変更せず、`status` と `updated_at` から初期読み込み対象を判定できる。
- 未完了タスクは従来どおり初期表示・検索・詳細表示できる。
- 直近完了タスクは完了ビューや検索で従来どおり扱える。
- 古い完了タスクは完了ビューまたは明示操作で追加読み込みできる。
- 検索では、古い完了タスクも初期状態から対象に含められる。
- 完了ビューでは、初期表示分を超える完了タスクを「次を読み込む」などのボタンで追加表示できる。
- タスクファイル正本と `_index.yaml` の整合性が崩れない。

## ユーザー確認ポイント

### 決定事項

- 直近完了タスクの範囲は「件数」で決める。
- 初期読み込みする完了タスク件数の既定値は 100件 とする。
- 「次を読み込む」1回あたりの追加件数は 100件 とする。
- 初期表示分を超える完了タスクは、「次を読み込む」などのボタン操作で追加読み込みする。
- 検索では、古い完了タスクも初期状態から対象に含める。
- 古い完了タスク検索は、grep 型のオンデマンド検索方式を採用する。
- 完了ビューを開いた時点では、古い完了タスクを自動読み込みしない。
- 未読み込みの古い完了タスク件数は画面に表示しない。
- 設定画面で読み込み範囲を変更できるようにする。

### 検索方式の検討メモ

- grep / ripgrep 系の検索は、基本的には検索実行時に対象ファイルを走査する。永続的な検索インデックスを必須にせず、ディレクトリ走査、ignore ルール、文字列探索の高速化で毎回検索する方式。
- VS Code などのエディタ検索も、ワークスペース全体検索では ripgrep のようなオンデマンド走査を使うことが多い。ファイル一覧やシンボル検索など、用途によっては別途インデックスを併用する。
- Codex がローカルワークスペースを探る場合も、通常は `rg` などで必要なタイミングに検索し、必要なファイルだけ読む。全ファイル本文を常時メモリへ読み込む前提ではない。
- Cotaska の CHG-083 では、起動時に古い完了タスク本文を全件読み込まない方針を優先する。
- そのため検索は、grep 型に近い「検索実行時に未読み込み完了タスクも対象ファイルから検索する」方式を採用する。
- 検索速度や件数が問題になる場合は、次段階として検索用の軽量インデックスを別仕様変更で検討する。
