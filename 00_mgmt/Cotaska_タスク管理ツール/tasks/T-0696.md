## 判断が必要な点

1. Microsoft Store経由の配布を優先するか。MSIXをStoreへ申請する場合、Microsoftの署名でStore経由のSmartScreen警告を回避できる。ただし既存NSIS版の自動更新、ユーザーデータ移行、Store審査、公開アカウントの運用設計が必要。
2. GitHub ReleasesでのNSIS配布を維持するか。その場合は公開信頼のあるコード署名を導入する。発行元名が表示され、継続配布で評価を積み上げられるが、警告の完全消失は保証されない。
3. 両方を提供する場合は主たるダウンロード導線と更新経路を決める。

## 完了条件

利用者が主経路と許容する初期警告、予算、公開名を決め、後続実装の対象を確定する。

## 2026-10-10 比較結果

| 項目 | Microsoft Store の MSIX | GitHub Releases の NSIS＋公開コード署名 |
| --- | --- | --- |
| SmartScreen | Storeからの取得・インストールでは警告を避けられる。現在のGitHub配布インストーラには効果がない | 発行元を示して評価を蓄積できるが、署名直後や新しい版では警告が残り得る |
| 直接費用 | 新しい開発者登録フローの登録料は無料。StoreがMSIXを再署名するため証明書購入は不要 | OV証明書の目安は年150～300米ドル。見積もり、HSM／トークン費用、税金は別途確認が必要 |
| 利用者の作業 | MicrosoftアカウントでPartner Centerに登録し、発行者情報・アプリ掲載情報・審査対応を行う | 個人／法人名義で証明書の本人確認、契約、鍵管理を行う。日本の個人・法人ではMicrosoft Artifact Signingの現行提供地域に該当しない可能性が高く、契約前に確認が必要 |
| Cotaska側の変更 | 現行electron-builder v26のAppXターゲット、Store用パッケージID・アイコン、データ保存先と既存NSISからの移行、Store更新とelectron-updaterの切替を設計・実装・検証する | 現行NSIS配布・GitHub更新を維持し、ビルド署名と署名検証を追加する。既存のsignAndEditExecutable=falseには過去のビルド権限問題という理由があるため、安易な切替はしない |
| 公開・更新 | Store審査とStore配信。Store版はStoreの更新機構に合わせる | 既存のGitHub Releases公開とelectron-updaterを継続 |

Microsoft Storeへ既存のEXEをそのまま登録する案では、EXEおよび含まれるPEファイルの公開信頼ある署名が別途必要。無償署名の利点を得るにはMSIX経路を選ぶ。

### 判断材料

- 警告を出さないことを最優先するならStore MSIXが適する。ただしユーザーがGitHubのEXEを直接使う場合には元の警告が残る。
- 今の配布方式を維持することを最優先するならOVなどの公開コード署名が適する。警告の完全解消は達成条件にできない。
- Cotaskaのタスクデータはプロジェクトフォルダに存在し、Storeパッケージのファイル配置・AppData仮想化・自動更新との整合を確認する必要がある。移行の難しさは現時点では未検証。
- コード確認では、プロジェクト本体は利用者が選ぶ外部フォルダ、最近使ったプロジェクト等の設定はElectronのuserData、インストール版の更新はelectron-updaterを利用している。Store版では特にuserDataの移行・更新処理の分岐を検証する必要がある。

## 利用者の選択（2026-10-10）

現時点ではMicrosoft Storeに公開せず、コード署名の費用も負担しない。GitHub Releasesでの直接配布を続け、無償で実行できる改善を優先する。将来のStore公開や有料署名は再検討可能だが、この対応の前提条件にしない。
