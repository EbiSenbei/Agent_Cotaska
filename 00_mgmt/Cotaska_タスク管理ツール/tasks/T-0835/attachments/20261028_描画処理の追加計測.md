# T-0835 描画処理の追加計測（2026-10-28）

## 結論

既存のviewport先行JSX生成、詳細のsort／親別集約memo、AiChatMessageのmemoが現行ソースに実装済みであることを確認し、再現可能な比較計測を追加した。製品ソースの追加変更は不要と判断。設計T-0839の保護条件を維持し、新たな仕様変更は行わない。

計測中に共有リポジトリへ利用者確認T-0840とT-0835の完了記録が追加されたため、その完了状態・完了日時を保持する。今回の定量値は利用者報告とは分けて記録する。

## 条件と測定対象

- Node 24.22.1、Electron 44.10.0、Chromium 152.0.7977.169、React開発版。隔離userData、オフスクリーン描画、backgroundThrottling無効。生成データとモックIPCのみ。実タスク・DBへの試験編集、AI通信、リリースは行わない。
- 対照は現行のMainPane／DetailPane／AiChatMessageに対して、T-0835のJSX先行slice、sort／reduceの非memo、メッセージの非memoをメモリ上だけ復元したもの。保存修正・依存版・既存Markdown content memoは両側で共通。過去配布版そのものとの比較ではない。
- 一覧1,000／5,000件、履歴500／2,000件。current→baseline→baseline→current→current→baselineの順に、別Electronプロセスで各3回。比較計測は直列で実施。
- scroll・本文入力・履歴親更新は1実行あたり5回（計15操作）、resize／drag-start／drag-over／dropは計3操作。
- 表の時間は各操作に含まれるReact Profiler actualDurationの合計の中央値。commit数もJSONへ保存。DOM commitフェーズ単体や入力から描画完了までの壁時計時間ではない。elapsedIncludingSettleMsは待機込みなので性能値に使わない。
- Long TaskはPerformanceObserverの50ms超イベント数で、計測区間内の全renderer処理を含む。Profilerの合計時間と同じ単位・範囲ではない。
- mount指標はDOMへの行／message挿入件数と生存DOM件数。React内部のfiber mount数ではない。初回・更新・削除の詳細は生JSONを参照。

## 処理回数と残る負荷

| 指標 | 対照 | 現行 |
|---|---|---|
| 1,000件 scroll 1操作のtitle参照 | 1,000〜2,000 | 31〜62 |
| 1,000件 詳細入力1操作のsort_order参照 | 1,998〜1,998 | 0〜0 |
| 5,000件 scroll 1操作のtitle参照 | 5,000〜10,000 | 31〜62 |
| 5,000件 詳細入力1操作のsort_order参照 | 9,998〜19,996 | 0〜0 |
| 500履歴 親更新1回のbody参照 | 500 | 0 |
| 2,000履歴 親更新1回のbody参照 | 2,000 | 0 |

- 一覧は450pxのviewportで31行、330pxへのresize後は29行を生存DOMとして確認（初回は高さ測定前の一時40行があり得る）。対照もDOM自体は仮想化しており、今回減るのは表示範囲外のJSX生成。scrollでは移動先31行を挿入し、入力・履歴親更新で不要な行／message再mountは発生しない。
- drag中は設計どおり仮想化を解除し1,000／5,000行をmountする。5,000件drag開始は対照320.5ms／現行338.5msで改善なし。drag overも136.0／150.2ms。drop後のReact描画は71.0→3.0msだが、全行DOM削除を含むLong Taskは残る。drag中の仮想化継続はdrag source・drop先・autoscrollの別設計と検証が必要で、本件で挙動を変更しない。
- AI履歴の初回は500／2,000メッセージ全件mountする。ページ分割を導入していないため、初回負荷は削減したとは扱わない。

## 回帰と検証限界

成功した項目：

- 両件数で5回scroll、viewport resizeをResizeObserverがReactへ反映、scroll位置保持。
- 一覧の未保存quick-add入力をsnapshot更新後も保持。日付由来のoverdue／due更新を次snapshotとして渡し、表示とscroll位置を維持。
- drag開始→over→dropのDOMイベントを通し、source／target ID・before移動payloadと仮想化復帰を確認。実正本は書き換えない。
- 両件数で詳細本文入力5回、外部の同一タスク更新後もdirty本文を保持し、500ms保存を確認。
- 両履歴件数で親更新5回、scroll位置、copy、タスクリンク、body差替え、添付filePath変更後の画像URL再取得を確認。
- 対照と現行の処理回数をassertし、ベースラインの復元が無効になった場合も失敗させる。
- 初回45ファイル207テスト、並行作業反映後の最終46ファイル210テストが成功。既存task-data隔離UIも成功（切替時flush・逆順IPC等）。履歴／待機UI結果は同添付ログを参照。

未確認／限定した項目：

- 実壁時計の午前0時をまたぐ常駐アプリの自動更新（今回は次snapshotを注入する境界テスト）。
- 同一filePathの画像ファイルを上書きした際の鮮度（今回はパス変更のみ）。
- OSのnative drag image・画面端autoscroll・実ウィンドウresizeの操作感、タッチ入力。
- 本番ビルドのProfilerによる測定、DOM commitフェーズ単体、長時間heap／cold start。
- ユーザー確認T-0840の問題なし報告は別途記録済みだが、上記の未実測条件まで確認済みと読み替えない。
