Codexと比べてチャットの応答速度が遅いと感じる。
Codexと比較して応答速度が上がるナニカがないか？調査してほしい

## 調査結果

結論として、Cotaska側だけで「モデルの実処理時間」を大きく短縮する余地は限定的。
ただし、体感速度の改善と、入力トークン削減による実処理時間の短縮余地はある。

### 現状確認

- CotaskaのAIチャットは `@openai/codex-sdk` をElectron main processから呼び出している。
- `20_app/src/main/codexSdkService.js` では `codexThread.runStreamed(prompt, { signal })` を使用しており、SDKのストリーミングイベント自体は受信している。
- 受信したイベントは `mainWindow.webContents.send("aiChat:runEvent", payload)` でrendererへ通知している。
- renderer側の `AiChatPane.jsx` では、処理中カードにイベント一覧として表示している。
- 一方で、最終的なassistantメッセージ本文は、処理完了後に `ai_messages` へ保存されたものを画面へ反映している。

### 遅く感じる主な理由

1. モデル側の推論時間
   - Codexはコーディング向けに推論・作業計画・ファイル確認を行うため、通常の短文チャットより応答に時間がかかる。
   - 複雑な依頼、長い参照ファイル、大きな作業フォルダではさらに遅くなる。

2. 参照ファイルによる入力増加
   - Cotaskaは選択された参照ファイルをプロンプト先頭に展開している。
   - 現在の初期値は「最大10ファイル、合計100,000文字」。
   - 参照が多いほど送信前処理、入力トークン、モデル処理時間が増える。

3. 体感速度の問題
   - 途中イベントは表示されるが、assistant本文そのものは完了後に反映される。
   - そのため、Codexアプリのように「文章が増えていく」感覚と比べると遅く感じやすい。

4. 計測値が不足している
   - 現状の `ai_runs` は開始・終了・エラーを保持できるが、以下のような細かい時刻は持っていない。
     - 送信開始
     - SDKロード完了
     - Codex thread開始/再開完了
     - 初回イベント受信
     - 初回agent_message受信
     - 最終応答保存完了
   - そのため、遅さの原因が「SDK起動」「認証/通信」「参照ファイル読み込み」「モデル推論」「UI反映」のどこかを定量的に判断しにくい。

## 公式情報から見た速度改善候補

Codex公式マニュアル上は、速度面で以下の選択肢がある。

参照元:

- OpenAI Codex Manual: `https://developers.openai.com/codex/codex-manual.md`
- 確認箇所: Speed、Codex SDK、Model selection

- Fast mode
  - 対応モデルの速度を上げる代わりにクレジット消費が増える。
  - CLIでは `/fast on`、設定では `service_tier = "fast"` と `[features].fast_mode = true` を使う方針が示されている。
  - ChatGPTサインイン時のCodex向け機能であり、APIキー利用時は標準API課金扱いになる。

- 軽量モデル
  - 公式マニュアルでは、重い作業には推奨モデル、軽い作業には `gpt-5.4-mini` のような高速・低コスト寄りモデルを使う考え方が示されている。
  - ただし、Cotaskaでは現時点でモデル選択UIを不要としているため、導入するなら設定画面側の任意項目として扱うのがよい。

- Codex-Spark
  - 近い将来の高速反復向け選択肢として公式マニュアルに記載がある。
  - ただし利用条件や提供範囲に制約があるため、Cotaskaの標準前提にはしない。

## 推奨対応

### 優先度高

1. 応答時間の計測ログを追加する
   - `ai_runs` に計測用カラムを追加する、または `ai_run_events` を追加する。
   - 最低限、以下を記録する。
     - `sent_at`
     - `sdk_loaded_at`
     - `thread_started_at`
     - `first_event_at`
     - `first_message_at`
     - `completed_at`
   - これにより「どこが遅いか」を次回以降に判断できる。

2. assistant本文の逐次表示を強化する
   - 現在は処理中カードへイベント表示しているが、`agent_message` の `item.text` を一時assistantメッセージとして表示・更新する。
   - 完了時にDB保存済みの最終assistantメッセージへ差し替える。
   - 実処理時間は変わらないが、体感速度は大きく改善しやすい。

3. 参照ファイル量を見える化する
   - 送信時に「参照ファイル数」「合計文字数」「切り詰め有無」を画面または実行ログへ表示する。
   - 重い場合はユーザーが参照を減らせるようにする。

### 優先度中

4. 設定画面に速度優先オプションを追加する
   - 例: `標準` / `速度優先`
   - 実装候補:
     - Codex config側のFast mode設定を利用できるか確認する。
     - SDKのthread optionまたは環境設定で `service_tier` 相当を渡せるか確認する。
   - SDKのTypeScript APIでFast modeを直接指定できるかは、実装前にSDKリポジトリ/型定義の確認が必要。

5. 軽量モデル選択を設定項目として追加する
   - ユーザー要望としてチャット入力欄のモデル選択ボタンは不要。
   - 追加するなら設定画面に「AIモデル（空ならCodex既定）」として置くのがよい。
   - ただしモデル一覧の取得仕様は別途調査が必要。

### 優先度低

6. Codex SDKインスタンスやthread再開の最適化を検討する
   - 現状は送信ごとに `new Codex()` している。
   - 効果があるかは不明なため、計測後に判断する。
   - 安易に永続化すると認証状態、キャンセル、複数スレッド同時送信、アプリ終了処理が複雑になる。

## 後続タスク候補

- AI応答時間の計測ログを追加する。
- `agent_message` の途中本文をチャット本文として逐次表示する。
- 参照ファイル数・文字数・切り詰め状態を送信前/処理中に表示する。
- Fast modeまたは速度優先設定をCodex SDKから利用できるか追加調査する。
- 設定画面に任意のモデル指定欄を追加するか検討する。

## 結論

すぐに効果が見込めるのは、実速度そのものよりも体感速度の改善。
特に `agent_message` の途中本文表示と、参照ファイル量の見える化を優先するのがよい。
そのうえで計測ログを入れ、実際に遅い箇所がSDK起動なのか、参照ファイルなのか、モデル推論なのかを切り分ける。

## 追加調査: Codex直接利用との速度差

同じ質問をCotaskaのAIチャットとCodex直接利用で比較した。

質問:

```text
今の時刻を教えてください。
また、この処理にかかった時間も図ってください
```

### Cotaska側の実測

Cotaskaの `data/ai.sqlite` を確認した。

対象run:

- `run_id`: `run_c397b951-796c-4fc2-8fd9-290fadc0f477`
- `thread_id`: `thread_fa23b2e5-c891-41cc-89d9-78d18ac5dfa9`
- `codex_thread_id`: `019f1d5a-bded-7423-82d4-0e3b0e9ce66d`
- sandbox: `danger-full-access`
- started_at: `2026-07-01T14:52:59.302Z`
- finished_at: `2026-07-01T14:53:25.434Z`

差分:

- 約 `26.132秒`

同じrunに紐づくメッセージ:

- user message created_at: `2026-07-01T14:52:59.304Z`
- assistant message created_at: `2026-07-01T14:53:25.436Z`

### Codex直接利用側の実測

ユーザー確認では、Codex直接利用では同じ質問が約 `5秒` で完了した。

### 該当Cotaskaスレッドの状態

Cotaska側の該当スレッドには、参照ファイルとして以下が付いていた。

- `data\tasks\T-0079.md`

ただし、このファイルは約328文字/20行程度であり、今回の26秒差の主因と断定するほど大きくはない。

スレッド履歴も以下の程度で、極端に大きくはなかった。

- user: 2件 / 約48文字
- assistant: 2件 / 約114文字

## 速度差の推定原因

現時点では、以下の複合要因と考える。

1. CotaskaはCodex SDK経由で呼び出している
   - Electron main processから `@openai/codex-sdk` を呼び、結果をSQLiteへ保存し、rendererへ反映している。
   - Codex直接利用より処理経路が長い。

2. Cotaskaは毎回 `new Codex()` している
   - `codexSdkService.sendMessage()` 内で送信ごとに `new Codex()` している。
   - SDK内部の初期化、接続、セッション準備が毎回発生している可能性がある。
   - ここが遅いかどうかは、追加した詳細ログで `open_ai_service_to_sdk_loaded` と `sdk_loaded_to_stream_started` を確認する必要がある。

3. Cotaskaは作業フォルダ・sandbox・参照ファイル付きの開発作業コンテキストで実行している
   - 単純な時刻質問でも、Codex SDK側では作業フォルダ付きのスレッド実行として扱われる。
   - Codex直接利用側の計測表示とは、内部で同じ条件ではない可能性がある。

4. 計測範囲が完全には一致していない
   - Cotaskaの26.132秒は、`ai_runs.started_at` から `ai_runs.finished_at` まで。
   - Codex直接利用の5秒は、画面に表示された作業時間。
   - どちらも参考値として有用だが、完全に同一の計測点ではない。

5. 追加ログがまだ有効な状態で再計測されていない
   - AI応答ログ追加後、Cotaska実行中のmain processが古いままだった可能性がある。
   - `logs/app-YYYY-MM-DD.log` には23時台の `AI chat assistant response` が出ていなかった。
   - 正確な内訳を見るには、Cotaskaを再起動してから再計測する必要がある。

## 追加の改善案

### 優先度高

1. Cotaska再起動後に詳細ログで再計測する
   - 追加済みの `AI chat request started` / `AI chat assistant response` ログで、以下を確認する。
     - `open_ai_service_to_sdk_loaded`
     - `sdk_loaded_to_stream_started`
     - `stream_started_to_first_event`
     - `stream_started_to_first_agent_message`
     - `stream_started_to_completed`
   - これにより、SDK初期化が遅いのか、Codex実行自体が遅いのかを切り分ける。

2. Codex SDKインスタンスの使い回しを検討する
   - 現状は送信ごとに `new Codex()`。
   - main process内でCodexインスタンスを保持し、送信ごとに再利用できるか検証する。
   - 期待効果:
     - SDK初期化時間の削減
     - 認証/接続準備の再実行削減
   - 注意点:
     - 複数スレッド同時送信
     - キャンセル処理
     - アプリ終了時の破棄
     - 認証状態変更時の再初期化

3. 単純質問では参照ファイルを送らない/軽くする設定を追加する
   - 現在は参照ファイルが付いていれば、質問内容に関係なくプロンプト先頭へ展開する。
   - 速度優先時は以下を選べるとよい。
     - 参照ファイルを送らない
     - 明示的に選択した場合だけ送る
     - 「このファイルを見て」などの文脈がある場合だけ送る

### 優先度中

4. 入力欄または設定に「速度優先」モードを追加する
   - 速度優先時の候補:
     - 参照ファイル自動展開を抑制
     - 軽量モデルを利用
     - Fast mode相当がSDKから指定可能か確認
   - Codex直接利用と同じFast mode/モデル設定をCotaska SDK経由で指定できるかは追加調査が必要。

5. `agent_message` の途中本文をチャット欄へ逐次表示する
   - 実時間が短くならなくても、体感速度は改善しやすい。
   - Codex直接利用に近い体験にするには、処理中カードだけでなく本文が伸びる表示が望ましい。

### 優先度低

6. 単純な一般質問をCodex SDKではなく軽量なAI経路へ分ける
   - ただしCHG-058の現行方針はCodex SDK利用。
   - AIプロバイダ拡張や一般チャット用途を広げる段階で検討する。

## 追加結論

今回の比較では、Cotaska側はCodex直接利用より明確に遅い。
まずは追加ログを有効化した状態で再測定し、遅延の内訳を確認する。

改善の第一候補は以下。

1. Codex SDKインスタンスの使い回し
2. 単純質問時の参照ファイル送信抑制
3. `agent_message` の途中本文表示
4. 速度優先設定の追加

この順で対応すると、実速度と体感速度の両方を改善しやすい。
