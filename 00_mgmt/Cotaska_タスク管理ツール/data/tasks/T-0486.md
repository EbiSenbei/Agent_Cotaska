設計書を、現在の仕様を示す正本と、経緯を残す仕様変更・不具合履歴に分けて読みやすくする。

作業内容:
- 設計書の目次と文書体系を作成する。
- 機能ごとに正本となる設計書を明示する。
- システム全体設計と基本設計の重複を整理する。
- CHG文書から現行設計へのリンクを追加する。
- 実装済み・未実装・廃止の状態を追跡できるようにする。

完了条件:
- 新規参加者が目次から現行仕様へ到達できる。
- 変更履歴を失わず、基本設計だけで現在の動作を把握できる。

## 文書体系再編方針（2026-07-17）

参照先 `night_business_ERP/10_docs` のうち、`night_business-Accounting_設計資料` を除外した構成を基準に、Cotaska の文書体系を次のように整理する。

```text
10_docs/
├─ 10_運用ルール/
├─ 20_設計/
│  ├─ 10_システム設計/
│  ├─ 20_基本設計/
│  ├─ 30_画面モック/
│  ├─ 40_DB設計/
│  └─ 50_共通資料/
└─ 30_変更管理/
   ├─ 10_仕様変更/
   └─ 20_バグレポート/
```

### Git履歴を維持する移行原則

- 削除・コピーによる置換は行わず、既存ファイルを `git mv` で移動する。履歴は移動後のファイルに対して `git log --follow -- <path>` で追跡できる状態を維持する。
- 移動だけを行うコミットと、本文・リンク・目次を更新するコミットを分離する。移動コミットでは内容を変更しないため、Git のリネーム検出率を高める。
- 大量移動は体系ごとに小さく分ける。移動後の本文更新も対象文書ごとに小さなコミットにし、変更前後の対応をレビュー可能にする。
- 移動前後で `git diff --summary -M` を確認し、意図したファイルが rename として検出されることを確認する。検出されない場合は内容変更を移動コミットから外し、再度確認する。
- 既存の CHG 文書、不具合報告書、テスト・リリース・DBスクリプトなどの履歴資料を削除しない。参照先に同名区分がない資料は、`30_変更管理` 配下に用途別の補助フォルダを設けて保全する。

### 実施順序

1. 現在の全資料について、移動元・移動先・正本または履歴の区分・参照更新先を対応表にする。
2. `git mv` のみで、運用ルール、設計書、仕様変更履歴、不具合報告書を新体系へ移動し、Git の rename 検出を確認してコミットする。
3. `20_設計/README.md`、機能一覧、画面一覧、DB一覧、実装ファイルと設計書の対応表を整備し、現在の正本を明示する。
4. システム全体設計と基本設計の重複を整理し、各設計書に実装済み・未実装・廃止の状態を記載する。
5. CHG 文書および不具合報告書から該当する現行設計へのリンクを追加し、旧パスを参照する運用ルール・文書内リンクを更新する。
6. リンク切れ、履歴資料の欠落、`git log --follow` による代表ファイルの履歴追跡を確認する。

### 完了時の確認観点

- 新規参加者が `20_設計/README.md` から現行設計の正本へ到達できる。
- `git log --follow` と Git の rename 表示で、移動前の主要文書の履歴を追跡できる。
- CHG 文書・不具合報告書・テスト・リリース資料を失わず、現行設計と履歴資料の役割が明確に分かれている。
