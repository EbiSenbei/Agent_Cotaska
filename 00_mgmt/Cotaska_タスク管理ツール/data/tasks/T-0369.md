## 目的

参照ファイルなし、短文入力でも `input_tokens` が約3万になる原因を調査し、応答速度改善の本命候補を切り分ける。

## 背景

T-0359の追加検証では、以下の条件でも `input_tokens: 29,529` が記録された。

- 参照ファイル: 0件
- prompt_chars: 36
- performance_mode: speed
- 合計応答時間: 約29.3秒

SDK読み込みやstream開始は短く、遅延の大半はCodex側の応答開始待ちだった。
そのため、Codex SDKが内部で渡している基礎コンテキスト、作業フォルダ情報、既存スレッド履歴、設定値などを確認する必要がある。

## 対応内容

- 参照ファイルなしの短文質問で `usage.input_tokens` が大きくなる条件を整理する。
- 新規スレッド/既存スレッドで入力トークン量が変わるか確認する。
- 作業フォルダ有無、sandbox、Codex thread再開有無が入力トークン量に影響するか確認する。
- Codex SDKやCodex側の既定プロンプト・リポジトリ文脈がどの程度含まれていそうか調査する。
- 必要に応じて、ログに以下の計測情報を追加する案を検討する。
  - thread新規/再開
  - reference_context有無
  - prompt_chars
  - usage.input_tokens
  - usage.cached_input_tokens

## 完了条件

- 参照なしでも入力トークンが大きい理由について、可能な範囲で仮説または根拠が整理されている。
- Cotaska側で削減できる余地と、Codex SDK/Codex側の固定文脈として削減しづらい領域が分かれている。
- 次に実装すべき改善案が判断できる。

## 調査結果

### 既存ログの比較

詳細ログが残っているAIチャットrunを比較した。

| 条件 | prompt_chars | 参照 | input_tokens | cached_input_tokens | 合計時間 |
|---|---:|---:|---:|---:|---:|
| 標準寄り・参照なし | 36 | 0件 | 29,474 | 24,320 | 15.225秒 |
| 速度優先・参照あり | 469 | 1件/328文字 | 29,944 | 19,712 | 12.391秒 |
| 速度優先・参照なし | 36 | 0件 | 29,529 | 20,224 | 29.258秒 |

読み取り:

- 参照ファイルなし、短文入力でも `input_tokens` は約29.5k。
- 参照ファイル328文字を追加しても、増加分は約470 tokens程度。
- したがって、約3万tokensの大半はCotaskaが生成したユーザープロンプトや参照ファイルではない。

### Cotaska側で渡している内容

`20_app/src/main/codexSdkService.js` を確認した。

参照ファイルなしの場合、Codex SDKへ渡す `prompt` はユーザー入力そのもの。
今回の時刻質問では `prompt_chars: 36` だった。

Codex SDKへ渡している主な指定:

- `workingDirectory`
- `sandboxMode`
- `approvalPolicy: "never"`
- `skipGitRepoCheck: true`
- `service_tier = "fast"` / `features.fast_mode = true`（速度優先時）

Cotaska側で、隠れた巨大プロンプトを追加している実装は見つからなかった。

### Codex SDK/CLI側の構造

`@openai/codex-sdk` の実装を確認した。

- SDKは内部で `codex exec --experimental-json` を起動する。
- `workingDirectory` は CLI の `--cd` として渡される。
- `modelReasoningEffort` は `--config model_reasoning_effort="..."` として渡される。
- `Usage.input_tokens` は `turn.completed` イベントでCodex CLI側から返る値であり、Cotaskaの `prompt_chars` とは別物。

公式マニュアル上も、Codexは以下を文脈として扱う。

- 作業スレッド内の情報
- ファイル内容
- ツール出力
- 作業記録
- `AGENTS.md`
- 設定やツール構成

また、Codexは作業フォルダからプロジェクトルートを検出し、`AGENTS.md` などのプロジェクト設定を読み込む。

### ローカル環境で確認した追加要素

この環境では以下が確認できた。

- リポジトリルート `AGENTS.md`: 約5,493文字 / 163行
- `~/.codex/config.toml`:
  - `model = "gpt-5.5"`
  - `model_reasoning_effort = "medium"`
- Codex CLIヘルプ:
  - `--ignore-user-config`
  - `--ignore-rules`
  - `--ephemeral`
  - `--config key=value`
  - `--cd`
  - `--sandbox`
- Codex公式情報:
  - ローカルタスクではWeb検索が既定で有効
  - `multi_agent` は既定で有効
  - `project_doc_max_bytes` の既定は32768 bytes

### 直接実行による軽量化実験

Cotaska外からCodex CLIを直接実行し、Web検索とmulti-agentを無効化して比較した。

実行条件:

- `web_search = "disabled"`
- `features.multi_agent = false`
- `model_reasoning_effort = "low"`
- `--ephemeral`
- `--sandbox read-only`
- `--cd Cotaska`

結果:

- `input_tokens`: 11,443
- `cached_input_tokens`: 0
- `output_tokens`: 72
- `reasoning_output_tokens`: 26

この結果から、Web検索/multi-agent/推論強度などのCodex実行プロファイルを絞ることで、入力トークンを大きく減らせる可能性がある。

ただし、PowerShell経由の日本語stdinが文字化けしたため、応答品質の比較としては扱わない。
トークン量の参考値として扱う。

### `minimal` 推論強度の注意

`model_reasoning_effort = "minimal"` も試したが、以下のエラーで失敗した。

```text
The following tools cannot be used with reasoning.effort 'minimal': image_gen.
```

このため、現行のCodexツール構成では `minimal` をそのまま既定採用するのは危険。
まずは `low` を候補にするのが現実的。

### `--ignore-user-config` の補足

`--ignore-user-config` も試したが、以下の結果だった。

- `input_tokens`: 20,482
- `cached_input_tokens`: 9,728

完全には軽くならず、プラグイン/スキル読み込みの警告も引き続き出ていた。
そのため、単純にユーザー設定を無視するだけでは十分ではない。

## 結論

参照なしでも入力トークンが約3万になる主因は、Cotaskaの参照ファイル展開ではなく、Codex CLI/agentが内部で持つ基礎文脈とツール構成の可能性が高い。

主な候補:

- Codexのシステム/開発者指示
- 作業フォルダ・プロジェクトルート検出
- `AGENTS.md`
- Web検索ツール
- multi-agent関連ツール
- インストール済みプラグイン/スキルのツール定義
- モデル/推論強度設定

Cotaska側で巨大なユーザープロンプトを作っているわけではない。

## Cotaska側で削減できる余地

効果が見込める順:

1. 速度優先モード時に `web_search = "disabled"` を渡す。
2. 速度優先モード時に `features.multi_agent = false` を渡す。
3. 速度優先モード時に `modelReasoningEffort = "low"` を渡す。
4. 必要に応じて `AGENTS.md` 読み込み量や `--ignore-rules` の扱いを検討する。
5. 参照ファイル送信抑制は、大きな添付がある場合の追加対策として有効。

## 次に実装すべき改善案

新規タスクとして、速度優先モード用の「軽量Codex実行プロファイル」を追加する。

候補設定:

```js
new Codex({
  config: {
    service_tier: "fast",
    web_search: "disabled",
    features: {
      fast_mode: true,
      multi_agent: false,
    },
  },
})
```

加えて、ThreadOptions側で以下を指定する。

```js
modelReasoningEffort: "low"
```

ただし `minimal` は `image_gen` ツールとの互換性エラーが出たため、現時点では採用しない。

## 追加検証: 同一スレッドの1回目/2回目比較

2026-07-03に、同一AIスレッドへ短文質問を2回投稿し、入力トークンと応答時間を比較した。

対象スレッド:

- `thread_id`: `thread_47047f4c-e3fc-4bd7-8ddc-78814b3ea551`
- `codex_thread_id`: `019f285e-0dbe-7383-952d-1f3626efff9e`
- performance_mode: `speed`
- fast_mode_requested: `true`
- 参照ファイル: 0件

質問:

```text
今の時刻を教えてください。
また、この処理にかかった時間も図ってください
```

2回目は以下の質問:

```text
再度今の時刻を教えてください。
また、この処理にかかった時間も図ってください
```

### 実測比較

| 回 | run_id | prompt_chars | input_tokens | cached_input_tokens | total | 初回イベント | 初回AI本文 |
|---|---|---:|---:|---:|---:|---:|---:|
| 1回目 | `run_9f44d4e2-98a7-4820-93cb-72a94792f9eb` | 36 | 29,522 | 24,320 | 22.888秒 | 8.519秒 | 16.433秒 |
| 2回目 | `run_48ab6478-a758-4741-92de-2970b7948dd3` | 38 | 59,604 | 49,152 | 10.016秒 | 1.140秒 | 3.862秒 |

DB上の差分:

- 1回目: 約 `22.858秒`
- 2回目: 約 `10.012秒`

### 読み取り

- 2回目はスレッド履歴が乗るため、`input_tokens` は約2倍に増えた。
- 一方で `cached_input_tokens` も約2倍に増えた。
- その結果、初回イベントまでの待ち時間は `8.519秒` から `1.140秒` へ短縮した。
- 初回AI本文までの待ち時間も `16.433秒` から `3.862秒` へ短縮した。
- つまり、同一スレッドの2回目以降は、基礎文脈や前回文脈がキャッシュされ、応答開始が速くなる可能性が高い。

### 補足

- トークン総量は増えるため、長いスレッドでは履歴肥大化により再び遅くなる可能性がある。
- ただし短い連続会話では、キャッシュ効果によって新規スレッド1回目より速くなる傾向がある。
- 今後の速度比較では、新規スレッド1回目と同一スレッド2回目以降を分けて評価する必要がある。
