AIチャットの連携先を Codex / Claude Code から選択できるよう、プロバイダ抽象化（aiProviderRegistry）を設計する。Claude は認証方式を2系統（ローカルサブスク認証 / クラウドプロバイダBedrock）持つ。

## 設計前提（確定事項 2026-07-13）

設計着手前にユーザーと確定した方針。設計本体はこれを土台とする。

1. **settings.yaml キー構造: プロバイダ別にネスト**
   - `aiChat.codex.{sandboxMode, performanceMode, model}` / `aiChat.claude.{permissionMode, performanceMode, model, authMode, bedrock.{region, modelId, awsProfile}}` のようにネストする。
   - 権限（sandboxMode/permissionMode）・AI速度（performanceMode）は Codex / Claude 各自に持つ（共通化しない）。
   - 既存のフラットキー（`aiChat.sandboxMode` 等）は codex 配下へ移行する。**mergeSettings に旧フラット→新ネストの移行ロジックを入れ、後方互換を維持する**（既存ユーザーの settings.yaml を壊さない）。
2. **実装スコープ: 両方式をフル実装**
   - ローカルサブスク認証 と Bedrock の両方を CHG-102 で実装する。
   - ただし PoC で動作確認できたのは Bedrock のみ。ローカル認証（`~/.claude/.credentials.json` がある環境）は確認タスク T-0438 で実機検証する（リスクとして明記）。
3. **AWS資格情報の保管: AWSプロファイル名のみ保存**
   - settings には `awsProfile`（プロファイル名）だけ保存し、実資格情報は AWS CLI/SDK の標準（`~/.aws`）に委ねる。アクセスキー等の実体は Cotaska に保存しない。
4. **配布ビルド判定: `app.isPackaged`**
   - `app.isPackaged === true`（パッケージ版）のときローカルサブスク認証モードを無効化/非表示にし、Bedrock のみ選択可能にする。開発ビルドでは両方選択可。


- プロバイダ依存は IPC の5メソッド（sendMessage / checkAuthStatus / cancelRun / listActiveRuns / listRunEvents）のみ。DB(aiService)・UI・参照ファイルは共用。
- settings.yaml に `aiChat.provider`（"codex" | "claude"）、`aiChat.claudeAuthMode`（"local" | "bedrock"）、Bedrock 用項目（region / modelId 等）を追加。未設定/不正値は provider="codex"、claudeAuthMode="local" にフォールバック。
- Claude 認証2系統の配布可否を定義:
  - ローカルサブスク認証（~/.claude/）… 個人利用限定・配布不可。
  - クラウドプロバイダBedrock（CLAUDE_CODE_USE_BEDROCK=1 + AWS資格情報）… 規約クリーン・配布可・従量課金。
  - 配布ビルドではローカル認証を無効化/非表示にし、Bedrock のみ配布対象とする。
- sandboxMode → permissionMode のマッピングを定義。
- 返却スキーマは両プロバイダで統一する。AWS資格情報は平文保存しない。

## 設定画面のグルーピング

AI関連の設定項目を、以下の3グループに分けて表示する。

- **AI共通**: 連携先（provider: Codex / Claude Code）の選択、および両プロバイダで共用する項目
  - 連携先セレクト、作業フォルダ、AI参照上限（送信方法・件数・文字数）、AIデータ削除（保持日数）、AI診断ログ
- **AI-Codex関連**: provider="codex" のときに使う項目
  - Codexモデル、権限（sandboxMode）、AI速度（performanceMode）、Codex認証状態
- **AI-ClaudeCode関連**: provider="claude" のときに使う項目
  - 認証方式（ローカルサブスク / クラウドプロバイダBedrock）、Claudeモデル、Bedrock設定（region / modelId / AWS資格情報）、Claude認証状態

表示方針:
- 選択中の provider に応じて「AI-Codex関連」「AI-ClaudeCode関連」を出し分ける（非選択側は非表示または不活性）。「AI共通」は常時表示する。
- 権限（sandboxMode）は共通保存値だが、Claude では permissionMode へ変換されるため、表記はグループ内で provider に合わせる。
- 配布ビルドでは「AI-ClaudeCode関連」のローカルサブスク認証を無効化/非表示にする（Bedrock のみ）。
- 各項目の settings.yaml 上のキー配置（共通/Codex固有/Claude固有）を設計で確定する。

# 設計本体

## 1. アーキテクチャ

```
[renderer] AiChatPane.jsx / SettingsPane.jsx
    │  window.cotaskaAPI.aiChat.*
    ▼
[main] main.js  ipcMain.handle("aiChat:*")
    │  provider = settingsService.getSettings().settings.aiChat.provider  ("codex" | "claude")
    ▼
aiProviderRegistry.js（新設）
    resolveProvider(provider) => provider === "claude" ? claudeCodeService : codexSdkService
    ├─ "codex"  → codexSdkService（既存・変更なし）
    └─ "claude" → claudeCodeService（新設・codexSdkService と同一シグネチャ）
    ▼
[main] aiService（DB系: ai.sqlite。両プロバイダ共用・変更なし）
```

- **プロバイダ依存は IPC の5メソッドのみ**: `sendMessage` / `checkAuthStatus` / `cancelRun` / `listActiveRuns` / `listRunEvents`。
- main.js の該当ハンドラは、直接 `codexSdkService.xxx` を呼ぶのをやめ、`aiProviderRegistry.resolveProvider(provider).xxx` を呼ぶ。
- DB系ハンドラ（listThreads / addMessage / listReferences / createProposal 等）は `aiService` のまま変更しない。
- `claudeCodeService` は `codexSdkService` と同一シグネチャ・同一返却スキーマを実装する共通インターフェースとする。

### 1.1 共通インターフェース（両サービスが実装）

| メソッド | 引数 | 返却 |
|---|---|---|
| `sendMessage(input)` | `{ thread_id, content, workdir, model, request_id, onEvent, ... }` | `{ ok, thread, run, userMessage, assistantMessage, items, usage, error?, error_kind? }` |
| `checkAuthStatus()` | なし | `{ ok, status, label, message, checkedAt, needsLogin, version?, checks? }` |
| `cancelRun(requestId)` | `requestId` | `{ ok, canceled? , error? }` |
| `listActiveRuns()` | なし | `Array<{ request_id, run_id, thread_id, ... }>` |
| `listRunEvents(input)` | `{ request_id \| run_id \| thread_id }` | `Array<event>` |

- `onEvent(payload)` を通じて `aiChat:runEvent` を renderer へ送出する仕組みは Codex と共通。payload 形（`{ request_id, thread_id, run_id, type, event }`）も統一する。

## 2. settings.yaml データ構造

プロバイダ別にネストする。既存フラットキーは codex 配下へ移行する（後述 6章）。

```yaml
aiChat:
  provider: "codex"            # "codex" | "claude"。未設定/不正値は "codex"
  workdir: ""                  # 共通（両プロバイダの作業フォルダ）
  referenceSendMode: "always"  # 共通（always / manual / skip-in-speed）
  maxReferenceFiles: 10        # 共通
  maxReferenceChars: 100000    # 共通
  diagnosticsEnabled: false    # 共通
  retentionDays: 90            # 共通
  codex:
    model: ""                  # 既定は codexSdkService の DEFAULT_CODEX_MODEL
    sandboxMode: "read-only"   # read-only / workspace-write / danger-full-access
    performanceMode: "standard" # standard / speed
  claude:
    model: "claude-opus-4"
    performanceMode: "standard"
    authMode: "local"          # "local" | "bedrock"。未設定/不正値は "local"
    permissionMode: "acceptEdits" # plan / acceptEdits / bypassPermissions
    bedrock:
      region: ""               # authMode=bedrock 時 必須
      modelId: ""              # authMode=bedrock 時 必須
      awsProfile: ""           # authMode=bedrock 時 必須（プロファイル名のみ。実体は ~/.aws）
```

- **共通キー**: `provider` / `workdir` / `referenceSendMode` / `maxReferenceFiles` / `maxReferenceChars` / `diagnosticsEnabled` / `retentionDays`。
- **codex固有**: `codex.{model, sandboxMode, performanceMode}`。
- **claude固有**: `claude.{model, performanceMode, authMode, permissionMode, bedrock.{region, modelId, awsProfile}}`。
- AWS の実資格情報（アクセスキー/シークレット）は保存しない。`awsProfile` 名のみ保存し、実体は AWS CLI/SDK の `~/.aws` に委ねる。

### 2.1 正規化・バリデーション（settingsService）

- `provider`: `["codex","claude"]` 以外 → `"codex"`。
- `claude.authMode`: `["local","bedrock"]` 以外 → `"local"`。
- `codex.sandboxMode` / `claude.permissionMode` / 各 `performanceMode`: 既存同様に許可値へ正規化。
- **Bedrock必須チェック**: `provider==="claude" && claude.authMode==="bedrock"` のとき、`claude.bedrock.region` / `modelId` / `awsProfile` の**3つが必須**。空欄があれば保存時にエラー（`validateAiWorkdir` と同様のバリデーション関数を追加）。モックの検証仕様（`settings_ai_provider_mock.html`）と一致させる。
- **配布ビルドガード**: `app.isPackaged === true` のとき `claude.authMode==="local"` は不可とし、`"bedrock"` に矯正（または保存拒否）。

## 3. claudeCodeService の処理設計

`codexSdkService.js` を雛形に、`@anthropic-ai/claude-agent-sdk` の `query()` を使う。

### 3.1 sendMessage

1. `aiService.openAiService()` → スレッド解決/作成、run 作成、user メッセージ保存（Codex と同じ流れ）。
2. 認証モードに応じて **環境変数を組み立てて** SDK 実行環境へ渡す:
   - `local`: 追加の環境変数注入なし（`~/.claude/` 認証を利用）。
   - `bedrock`: `CLAUDE_CODE_USE_BEDROCK=1`、`AWS_PROFILE=<awsProfile>`、`AWS_REGION=<region>`、モデルは `bedrock.modelId` を使用。
3. 参照ファイル前置き（`buildReferenceContext` 相当）は Codex と**共通ロジックを流用**（プロバイダ非依存の共通モジュールへ切り出す）。
4. `query({ prompt, options })` を実行し、`options` に以下を渡す:
   - `cwd`: workdir
   - `permissionMode`: sandboxMode→permissionMode 変換（4章）／claude は `claude.permissionMode`
   - `model`: `claude.model`（bedrock 時は `bedrock.modelId`）
   - `abortController`: キャンセル用（5章）
   - `maxTurns`: 既定値（暫定 15、実装時に調整）
5. `for await (const message of q)` でストリーミングし、`emitRunEvent` で UI へ流す。メッセージ種別のマッピングは 3.2。
6. 完了後、`assistantMessage` を保存、`usage` を変換してトークン数記録（7章）、run を completed に更新。

### 3.2 ストリーミングのイベントマッピング（PoC結果反映）

Claude SDK のメッセージは `system(init) → assistant → result` の順（PoC確認済み）。Codex の event へマッピングする。

| Claude message | 意味 | Cotaska 側の扱い |
|---|---|---|
| `type: "system"`, `subtype: "init"` | 開始・model情報 | run 開始イベント。`message.model` を記録 |
| `type: "assistant"` | 応答本文 | `message.message.content[]` の `type==="text"` を連結し、逐次 UI 反映。最終値を finalResponse に |
| `type: "result"` | 完了 | `subtype`（success 等）、`is_error`、`duration_ms`、`total_cost_usd`、`usage` を取得。`is_error===true` は失敗扱い |

- UI 側の `aiChat:runEvent` の payload 形は Codex と統一する（renderer は provider を意識しない）。

## 4. sandboxMode → permissionMode マッピング

| Cotaska（codex.sandboxMode 相当の概念） | Claude permissionMode |
|---|---|
| `read-only` | `plan`（読み取り・計画のみ） |
| `workspace-write` | `acceptEdits`（作業フォルダ内の編集を承認） |
| `danger-full-access` | `bypassPermissions`（要注意・警告表示） |

- Claude 側は `claude.permissionMode` を直接持つため、UI では上記の対応表記で選択させる（モック準拠）。
- `bypassPermissions` は SDK 側で opt-in が必要な場合があるため、実装時に確認する。

## 5. キャンセルの扱い（PoC結果反映・Codexと差異あり）

- Codex は abort 時に `AbortError` を throw する前提だった。
- **Claude は abort 時に例外を投げず、`system(init)` 受信後にストリームが静かに終了する**（PoC確認: result 未受信・catch にも入らない）。
- よって claudeCodeService では **「result を受信したか」フラグ**を持ち、`result` 未受信のままループが終了した場合を**キャンセル（中断）扱い**とする。
  - abortController.signal.aborted が true、または result 未受信でループ終了 → run を `canceled` に更新し、「AI処理を中断しました。」メッセージを保存（Codex のキャンセル時と同じ返却）。
- `cancelRun(requestId)` / `listActiveRuns` / `listRunEvents` は Codex の activeRequests 管理ロジックをほぼ流用する。

## 6. 既存 settings.yaml の後方互換移行

- 旧: `aiChat.sandboxMode` / `aiChat.performanceMode` /（旧 model 相当）がフラットに存在。
- 新: `aiChat.codex.{sandboxMode, performanceMode, model}`。
- `settingsService.mergeSettings` に移行ロジックを追加:
  - `aiChat.codex` が無く、旧フラットキーがある場合 → 旧値を `aiChat.codex.*` へ移送。
  - 移行後は新ネスト構造で `renderSettingsYaml` により再出力（コメント付き）。
  - 共通キー（workdir / referenceSendMode / maxReference* / diagnosticsEnabled / retentionDays）は `aiChat` 直下のまま維持。
- これにより既存ユーザーの設定を壊さず、初回読み込み時に自動移行される。

## 7. usage / トークン数の変換

- Codex: `usage.{input_tokens, output_tokens, reasoning_output_tokens}` を合算。
- Claude(result): `usage.{input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens}` と `total_cost_usd`。
- `aiService.addMessage` の `token_count` へは、Claude では `input_tokens + output_tokens`（cache 系は補助情報）を格納する変換関数を用意。
- 診断ログ（diagnosticsEnabled）には Claude の `total_cost_usd` / cache トークンも出力可能とする。

## 8. checkAuthStatus（Claude）

- `codex doctor` 相当の専用コマンドは無い（PoC確認）。
- 判定手順:
  1. `authMode==="bedrock"`: `awsProfile` / `region` / `modelId` の設定有無を確認 → 未設定なら `login_required` 相当。
  2. 軽いテストクエリ（短いプロンプトで `query()` を1回、`maxTurns:1`）を投げ、`result` が返れば `available`、認証系エラーなら `login_required` / `expired_possible`、それ以外は `error`。
- 返却スキーマは Codex の `sanitizeAuthStatusResult` と統一（`status` / `label` / `message` / `checkedAt` / `needsLogin` / `version?`）。ラベルは Claude 用に文言調整。

- `app.isPackaged` が true のとき、ローカル認証ラジオを非活性/非表示にする。

- DB系ハンドラは変更しない。

## 12. リスク・確認事項

- **ローカル認証は未検証**（PoCはBedrockのみ）。T-0438 で `~/.claude/.credentials.json` がある環境での実機確認が必要。

- **`bypassPermissions` の opt-in 要否**を実装時に確認。
- 返却スキーマ統一を崩さないよう、claudeCodeService の各返却を Codex と突き合わせて検証する。
